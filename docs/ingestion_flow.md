# Ingestion Flow Documentation

This document explains the current ingestion and Bronze validation version of the Financial Market Data project.

At this stage, the project does two closely related things:

```text
Fetch market data from external APIs and store the raw responses as local JSON files.
Validate those local Bronze JSON files before any later transformation work.
```

There are no transformations, Silver layer, Gold layer, SQL tables, PostgreSQL loading, or Spark jobs in the current version.

## Current Architecture

```text
Yahoo Finance / Binance
        |
        v
Python ingestion clients
        |
        v
Bronze JSON writer
        |
        v
data/bronze/
        |
        v
Bronze validator
        |
        v
Optional quarantine to data/rejected/
```

The goal is to build the project slowly and clearly. Right now, we care about collecting raw data, storing it locally in a clean folder structure, and checking that the raw files are usable.

## What Each Folder Does

### `src/ingestion/`

This contains all code related to getting data from external sources and saving it locally.

It has four main files:

```text
yahoo_client.py
binance_client.py
bronze_writer.py
ingest.py
```

### `src/pipeline/`

This contains the command-line entrypoint.

The main file is:

```text
run_daily.py
```

When you run the project, this is the file that controls the overall flow.

### `src/validation/`

This contains code that checks the Bronze JSON files after ingestion.

The main file is:

```text
validate_bronze.py
```

It checks file existence, JSON readability, required fields, numeric values, duplicate timestamps, date ranges, and optional quarantine.

### `src/utils/`

This contains shared helper code:

```text
config.py
logger.py
```

`config.py` stores project settings such as symbols and folder paths.

`logger.py` controls how logs are printed to the terminal.

### `tests/`

This contains unit tests.

Right now the tests check the API client logic and the Bronze validation logic.

### `data/bronze/`

This is where raw JSON files are saved.

This folder is generated by the pipeline and is ignored by Git.

### `data/rejected/`

This is where invalid Bronze files are moved if validation is run with quarantine enabled.

This folder is generated by validation and is ignored by Git.

## Main Command

The main command is:

```powershell
python -m src.pipeline.run_daily --start-date 2026-06-01 --end-date 2026-06-05
```

This command means:

```text
Run the ingestion pipeline.
Fetch data starting from 2026-06-01.
Stop before 2026-06-05 if the source supports an end date.
Save the raw API responses as JSON files.
```

If you do not provide a start date, the default is:

```text
2023-01-01
```

## Step-By-Step Runtime Flow

When you run:

```powershell
python -m src.pipeline.run_daily --start-date 2026-06-01 --end-date 2026-06-05
```

Python starts inside:

```text
src/pipeline/run_daily.py
```

The flow is:

```text
1. Parse command-line arguments
2. Create required data folders
3. Generate a run ID
4. Call the ingestion layer
5. Fetch Yahoo Finance data
6. Fetch Binance data
7. Save each response as JSON
8. Validate the Bronze JSON files
9. Print ingestion and validation summaries to the terminal
10. Fail the command if validation has more than 25% invalid files
```

## `run_daily.py`

This file is the pipeline controller.

It does not talk to Yahoo or Binance directly. Instead, it calls:

```python
ingest_all(...)
```

The important function is:

```python
run_daily(start_date, end_date, retries)
```

Inside this function:

```python
ensure_data_dirs()
```

creates the local data folder if it does not exist.

Then:

```python
run_id = f"run_{uuid4().hex[:12]}"
```

creates a unique ID for the run.

Example:

```text
run_9f42180d5ffe
```

Then:

```python
ingestion_results = ingest_all(...)
```

starts fetching data from the APIs.

At the end, the code counts how many files succeeded and how many failed:

```python
successes = sum(1 for result in ingestion_results if result["status"] == "success")
failures = len(ingestion_results) - successes
```

Then it prints a final log message.

After ingestion, `run_daily.py` calls:

```python
validate_bronze_file_level(run_date)
```

That checks the Bronze files created for the current run date.

Then it builds a validation summary:

```python
build_validation_summary(validation_results, validation_failure_threshold)
```

If more than 25% of expected files are invalid, the command returns a failing exit code.

## `ingest.py`

This is the ingestion coordinator.

It creates one Yahoo client:

```python
yahoo = YahooClient()
```

and one Binance client:

```python
binance = BinanceClient()
```

Then it loops over all configured symbols.

For equities:

```python
for symbol in EQUITY_SYMBOLS:
```

it calls Yahoo Finance.

For FX:

```python
FX_SYMBOL
```

it also calls Yahoo Finance.

For crypto:

```python
for symbol in CRYPTO_SYMBOLS:
```

it calls Binance.

Every API request goes through:

```python
_with_retry(...)
```

This gives each symbol multiple attempts before it is marked as failed.

## Retry Logic

The retry logic exists because APIs are not always reliable.

The default is:

```text
3 attempts per symbol
```

If one attempt fails, the code logs a warning and waits briefly before trying again.

The wait time grows slightly:

```python
sleep(min(attempt * 2, 10))
```

That means:

```text
Attempt 1 fails -> wait 2 seconds
Attempt 2 fails -> wait 4 seconds
Attempt 3 fails -> stop
```

If all attempts fail, the result looks like:

```python
{
  "source": "binance",
  "symbol": "BTCUSDT",
  "status": "failed",
  "records_loaded": 0,
  "path": None,
  "error": "..."
}
```

If it succeeds, the result includes the saved JSON path.

## `yahoo_client.py`

This file handles Yahoo Finance data through `yfinance`.

The key method is:

```python
get_daily_prices(symbol, start_date, end_date)
```

It calls:

```python
yf.Ticker(symbol).history(...)
```

with:

```text
interval = 1d
auto_adjust = False
```

The Yahoo data comes back as a pandas DataFrame.

The code converts that DataFrame into JSON-friendly records:

```python
frame.to_dict(orient="records")
```

The final payload shape is:

```json
{
  "source": "yahoo",
  "symbol": "CBA.AX",
  "start_date": "2026-06-01",
  "end_date": "2026-06-05",
  "interval": "1d",
  "records": []
}
```

The actual `records` list contains daily OHLCV rows.

OHLCV means:

```text
Open
High
Low
Close
Volume
```

## `binance_client.py`

This file handles Binance crypto data.

The key method is:

```python
get_daily_klines(symbol, start_date, end_date)
```

It calls:

```text
https://api.binance.com/api/v3/klines
```

with parameters like:

```text
symbol=BTCUSDT
interval=1d
startTime=...
limit=1000
```

Binance uses timestamps in milliseconds, so the code converts normal dates into milliseconds:

```python
_date_to_ms(...)
```

The Binance response is a list of lists.

Each row contains values such as:

```text
open time
open price
high price
low price
close price
volume
trade count
```

The final payload shape is:

```json
{
  "source": "binance",
  "symbol": "BTCUSDT",
  "start_date": "2026-06-01",
  "end_date": "2026-06-05",
  "interval": "1d",
  "records": []
}
```

## `bronze_writer.py`

This file saves API responses to disk.

The key function is:

```python
write_bronze(asset_class, source, symbol, payload, run_date)
```

It creates folders like:

```text
data/bronze/equities/source=yahoo/date=2026-06-15/
data/bronze/crypto/source=binance/date=2026-06-15/
data/bronze/fx/source=yahoo/date=2026-06-15/
```

Then it writes one JSON file per symbol.

Example:

```text
data/bronze/equities/source=yahoo/date=2026-06-15/CBA.AX.json
```

The `date=YYYY-MM-DD` folder is the ingestion run date, not necessarily the market date.

That means:

```text
The folder date tells you when you fetched the data.
The records inside the file tell you what market dates were fetched.
```

## Why This Is Called Bronze

Bronze means raw data.

At this stage, we do not clean or standardize the data.

The purpose of Bronze is:

```text
Store the original API response
Keep data source separation
Allow replay later
Allow debugging later
Preserve what was fetched
```

This is an important Data Engineering pattern.

Later, when transformation is added back, Bronze will be the input for Silver.

## Bronze Validation: Steps 1 To 12

The project now has all twelve Bronze validation steps implemented in:

```text
src/validation/validate_bronze.py
```

This does not clean the data yet. It checks whether the expected raw JSON files exist, whether they can be parsed, and whether their basic payload and record structures match the expected source format.

Run validation with:

```powershell
python -m src.validation.validate_bronze --run-date 2026-06-16
```

You can also run the file directly:

```powershell
python src\validation\validate_bronze.py --run-date 2026-06-16
```

To move invalid existing files into the rejected folder, run:

```powershell
python -m src.validation.validate_bronze --run-date 2026-06-16 --quarantine
```

The normal validation command does not move files. Quarantine only happens when `--quarantine` is included.

### Step 1: Locate Expected Bronze Files

The function:

```python
locate_expected_bronze_files(run_date)
```

builds the list of files that should exist for a run date.

For the current config, it expects:

```text
5 Yahoo equity files
1 Yahoo FX file
5 Binance crypto files
```

Total:

```text
11 expected Bronze JSON files
```

Example expected paths:

```text
data/bronze/equities/source=yahoo/date=2026-06-16/CBA.AX.json
data/bronze/fx/source=yahoo/date=2026-06-16/AUDUSD=X.json
data/bronze/crypto/source=binance/date=2026-06-16/BTCUSDT.json
```

The output of this step is a list of `ExpectedBronzeFile` objects.

Each object stores:

```text
asset_class
source
symbol
path
```

### Step 2: File-Level Checks

The function:

```python
validate_file(expected_file)
```

checks one expected file.

It currently checks:

```text
file extension is .json
file exists
path is a file, not a folder
file size can be read
file is not empty
file can be parsed as valid JSON
```

The function:

```python
validate_bronze_file_level(run_date)
```

runs those checks for every expected Bronze file for the run date.

The output is a list of `FileValidationResult` objects.

Each result stores:

```text
asset_class
source
symbol
path
status
file_size_bytes
errors
```

Example terminal output:

```text
Validated 11 expected Bronze files: 11 valid, 0 invalid
VALID   CBA.AX       data/bronze/equities/source=yahoo/date=2026-06-16/CBA.AX.json
VALID   BTCUSDT      data/bronze/crypto/source=binance/date=2026-06-16/BTCUSDT.json
```

### Step 3: Top-Level JSON Structure Checks

After the file is confirmed to be readable JSON, the validator checks that the payload is a JSON object.

It then checks for these top-level fields:

```text
source
symbol
start_date
end_date
interval
records
```

It also checks:

```text
source matches the expected source
symbol matches the expected symbol
records is a list
records is not empty
```

Example:

```text
BTCUSDT.json should contain source = binance
BTCUSDT.json should contain symbol = BTCUSDT
```

### Step 4: Yahoo Record Checks

For Yahoo files, each item in `records` should be a JSON object.

Each Yahoo record is checked for:

```text
Date
Open
High
Low
Close
Volume
```

The numeric fields are checked to make sure they are:

```text
numeric
not negative
```

This applies to both:

```text
equities from Yahoo
FX reference data from Yahoo
```

### Step 5: Binance Record Checks

For Binance files, each item in `records` should be a list.

Each Binance record must have at least 12 fields:

```text
0  open_time
1  open_price
2  high_price
3  low_price
4  close_price
5  volume
6  close_time
7  quote_asset_volume
8  number_of_trades
9  taker_buy_base_asset_volume
10 taker_buy_quote_asset_volume
11 ignore
```

The validator checks that:

```text
open_time is a non-negative integer
close_time is a non-negative integer
close_time is greater than open_time
prices are numeric and not negative
volumes are numeric and not negative
number_of_trades is a non-negative integer
```

These checks are still structural/data-type checks. More advanced business rules can be added later.

### Step 6: Duplicate Timestamp Checks

The validator checks for duplicate market timestamps inside each file.

For Yahoo files, the timestamp is:

```text
Date
```

For Binance files, the timestamp is:

```text
open_time
```

This is important because daily market data should normally have one row per asset per day.

Example problems:

```text
CBA.AX has two records for 2026-06-01
BTCUSDT has two records with open_time 1780272000000
```

The validator does not delete duplicate records from Bronze.

That is intentional. Bronze is raw storage, so validation reports the problem instead of rewriting the source file.

### Step 7: Date Range Checks

Each payload stores:

```text
start_date
end_date
```

The validator parses those fields and checks that each record date fits inside that range.

For Yahoo:

```text
record["Date"] must be on or after start_date
record["Date"] must be on or before end_date
```

For Binance:

```text
record[0] open_time is converted from milliseconds into a UTC date
that date must be on or after start_date
that date must be on or before end_date
```

If `end_date` is `null`, the validator only checks the lower bound.

This catches files where the payload says one date range but the records contain data from outside that range.

### Step 8: Missing Data Checks

The validator checks that required fields exist before trying to use them.

At the top level, each JSON file must have:

```text
source
symbol
start_date
end_date
interval
records
```

For Yahoo records, each row must have:

```text
Date
Open
High
Low
Close
Volume
```

For Binance records, each row must have at least 12 list items.

This means the validator catches missing data clearly, for example:

```text
missing top-level field records
record 0 missing field Date
record 0 missing field Close
record 0 has fewer than 12 fields
```

### Step 9: Quarantine Invalid Files

Quarantine means moving invalid files away from the normal Bronze folder.

The code path is:

```text
validate_bronze_file_level(run_date)
        |
        v
validate_file(expected_file)
        |
        v
quarantine_invalid_files(results)
        |
        v
quarantine_file(result)
```

If a file is invalid and exists on disk, it moves from:

```text
data/bronze/...
```

to:

```text
data/rejected/...
```

The relative folder structure is preserved.

Example:

```text
data/bronze/crypto/source=binance/date=2026-06-16/BTCUSDT.json
```

becomes:

```text
data/rejected/crypto/source=binance/date=2026-06-16/BTCUSDT.json
```

If the validation error is `file does not exist`, there is no file to move, so quarantine skips it.

### Step 10: Validation Summary

After all files are checked, the validator builds a summary object.

The function is:

```python
build_validation_summary(results, failure_threshold)
```

It counts:

```text
total_files
valid_count
invalid_count
failure_rate
failure_threshold
should_fail_run
```

The standalone validation command prints this summary after the file-by-file results.

Example:

```text
Validation failure rate: 0.00%
Validation failure threshold: 25.00%
Validation decision: PASS run
```

### Step 11: Failure Threshold

The MVP rule is:

```text
Fail the run if more than 25% of expected Bronze files are invalid.
```

The default threshold is stored in:

```text
src/utils/config.py
```

as:

```python
VALIDATION_FAILURE_THRESHOLD = 0.25
```

The rule uses `more than 25%`, not `25% or more`.

That means:

```text
25% invalid -> still pass
more than 25% invalid -> fail
```

You can override the threshold from the standalone validation command:

```powershell
python -m src.validation.validate_bronze --run-date 2026-06-16 --failure-threshold 0.10
```

### Step 12: Daily Pipeline Integration

The daily runner now validates Bronze files after ingestion.

The normal command is still:

```powershell
python -m src.pipeline.run_daily --start-date 2026-06-01 --end-date 2026-06-05
```

The flow is now:

```text
1. Ingest Yahoo and Binance data
2. Write raw Bronze JSON files
3. Validate the Bronze files for the run date
4. Print validation results and summary
5. Return a failing exit code if invalid files are above the threshold
```

If you want to skip validation for a temporary run:

```powershell
python -m src.pipeline.run_daily --start-date 2026-06-01 --skip-validation
```

If you want the daily runner to quarantine invalid files:

```powershell
python -m src.pipeline.run_daily --start-date 2026-06-01 --quarantine-invalid
```

Quarantine is explicit because it moves files.

## Current Project Goal

The current goal is:

```text
I can run one command and collect raw market data JSON files locally.
That same command validates the Bronze files before the next project stage.
I can also run validation by itself when I want to inspect an existing run date.
```

That is the foundation of the whole platform.

Once this is solid, the next natural stages are:

```text
1. Add metadata logs per run
2. Add Bronze to Silver transformation
3. Add Gold metrics

```

